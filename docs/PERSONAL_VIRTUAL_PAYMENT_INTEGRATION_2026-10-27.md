# 个人主体虚拟支付接入与验收

日期：2026-10-27，Asia/Singapore。用户已指定微信《虚拟支付：个人》为接入依据，并明确“尚未开通，先完成代码与可测试配置”。本期交付完整代码与隔离测试，平台开通、真实凭据、发布和真钱验证保留为明确待验项。

## 目标与事实基线

从现有购买页进入，取得服务端报价，使用微信登录态生成个人虚拟支付参数；通过服务端发货通知或查单确认付款，仅一次授予本人、指定探索快照的报告权益。前端成功回调、取消或网络错误都不能独立授予权益或认定付款失败。

接入前，购买页与查单使用本地模拟，支付及微信绑定只有契约骨架；已实现的正式关系报告使用旧产品域。本轮个人虚拟支付接口负责现有自我探索产品，普通微信支付接口保留原有边界。

本期使用现有两款报告及职业补差商品作为可测试商品配置（2990、4990、2000分），真实商品ID与价格须在开通后按后台发布的道具逐一配置。数量固定1，不增加代币、订阅或优惠计价。服务端冻结商品、金额、环境和输入快照指纹，客户端不提交成交金额。

## 最小实现范围

- 复用中央鉴权、Visitor会话、Envelope Encryption、Flyway和MyBatis。免费路径继续使用Visitor；购买时自动`wx.login`并由服务端`code2Session`验证，Principal等级表示当前会话已绑定微信。当前会话ID保留，支付买家另用稳定的AppID/OpenID派生标识，保护原访客资源与跨设备购买身份两个范围。
- 新增买家、微信会话密钥、订单、平台回执四种必须持久化的记录；敏感身份、会话密钥、冻结输入与回执用现有加密机制保护。订单保留可恢复的冻结输入和模板版本，已购读取必须通过本人权益接口，支持新会话恢复原输入；现有确定性报告模板的内容质量不因支付接入变成生产AI。现有业务没有可复用实现，新增迁移、协议适配、业务服务与测试因此超过默认两文件门限，范围限于本次支付闭环。
- 订单同一买家/商品/快照的未决购买复用原意图；OutTradeNo全局唯一，不为未知支付自动换单。金额为整数分，订单原支付事实与退款事实分别保存。
- 消息推送使用独立Token和安全模式AES；启用支付必须配置EncodingAESKey。验证`msg_signature`、解密AppID后解析；不允许将明文回调正文当作退款或发货证据。发货还必须以冻结订单和官方查单证据核对，成功统一回复纯文本`success`。
- 查单按冻结的OpenID、env、OutTradeNo执行，核对业务单号、环境、金额及平台内部订单号。请求env 0/1对应查询env_type 1/2。平台内部订单号作为权益幂等键；不把MchOrderNo强行等同wx_order_id。
- 支付状态2/3/4可形成付款证据；本地权益与回执同事务提交。查单补发还需平台发货确认；确认失败保留待确认状态供后续重试。状态5只表示退款商户扣款，状态8才表示用户到账；保留最初支付记录并按确认退款撤销权益。
- 补差冻结`base_order_id`并以唯一约束限制同一基础订单的有效升级；报价、创建、签名及授予权益均核对基础支付/退款状态。基础退款确认后暂停依赖它的升级权益，保留升级实际付款，转售后处理，不把已支付升级伪造为已退款。退款安全消息必须核对原支付单、买家、退款ID、金额与成功码；迟到发货不得恢复已撤销权益。
- 现有页面只从后台响应更新支付与权益，移除“查单即成功”和模拟支付/模拟退款的生产入口。样例报告继续明确为样例。

## 接口与测试边界

沿用用户指定指引的下单、推送、查单及权益界面作为验收边界：

1. `POST /api/v1/virtual-pay/quotes`：根据购买输入生成快照指纹、权威报价与当前权益。
2. `POST /api/v1/virtual-pay/orders`：本人已绑定微信，按报价版本创建唯一订单。
3. `GET /api/v1/virtual-pay/orders/{orderId}`：本人订单、支付/退款/权益状态。
4. `POST /api/v1/virtual-pay/orders/{orderId}/payment`：对冻结signData生成双签名。
5. `POST /api/v1/virtual-pay/orders/{orderId}/query`：查询原平台订单并幂等确认权益。
6. `GET/POST /api/v1/webhooks/wechat-virtual-pay`：URL验证及发货/退款消息。
7. `POST /api/v1/identity/wechat/bind`：复用原接口完成真实绑定。

测试按纵向切片推进：先固定字节签名/安全推送向量，再贯穿HTTP身份、报价、下单、待付款、发货、重复通知、补发、退款和越权拒绝；前端验证平台success不直接解锁、查询失败保持未知、报价只取服务端。平台边界使用隔离的本地HTTP替身，返回字段遵循官方文档并明确标注为测试证据。

## 组件边界与后续业务复用

当前是**可复用支付核心 + 报告接入层**，没有第二个后端业务接入的验收证据。

| 代码 | 职责 | 后续业务的接入工作 |
| --- | --- | --- |
| `WechatVirtualPayProtocol` | 固定字节双签名、消息 SHA1/AES、AppID 与 XML/JSON 校验 | 沿用同一微信协议 |
| `WechatVirtualPayGateway`、`VirtualPaySettings` | code2Session、稳定 token、查单、发货确认与通道配置 | 配置该小程序正式通道；隔离替身仅允许测试 profile 的回环地址 |
| `VirtualPaymentApplicationService`、`VirtualPaymentMapper` | 订单冻结、买家隔离、幂等、付款与退款事实、权益事务、查询顺序保护 | 当前仍调用报告策略、请求 DTO 和报告订单字段；新业务需扩展其接入契约和业务适配，不能原封不动挂接任意产品 |
| `report/application/GrowthReportPurchasePolicy` | 报告输入规范化、商品与价格、基础抵扣、依赖权益 | 各业务提供自己的商品、购买资格、交付与退款后权益规则 |
| `createVirtualPayment` SDK 工厂 | 登录、报价、原生支付、原订单查询、售后登记和权益读取编排 | 注入 API、身份管理、`state` 回调与 `loadEntitlement`；工厂不导入 growth-store |
| `getVirtualPayment` 与页面 | 本报告产品的 API 和状态接线 | 新业务使用自己的接线层与展示 |

复用保留的共同约束：客户端成功不发权益；同一个已开始支付的未知意图不再拉起；恢复单的SKU必须与本次报价一致，否则只展示原单；同一次尚未进入原生支付的流程若丢失签名 HTTP 响应，只以原会话、原幂等键取回一次；存在退款观察的原单不能签发支付参数；付款、退款与权益分别保存；确认退款不会擦除最初付款；旧查询响应不能回退新的退款观察。基础报告发生退款后，职业补差保留实付款并暂停依赖权益。

退款能力的当前范围是**认证通知、原单查证、退款 ID 去重、累计到账与权益处理**。售后接口只登记诉求，并明确返回 `refund_submitted=false`。Android 等终端可由商家在 MP 后台操作退款；iOS 由用户向 App Store 申请。本期没有开放主动 `refund_order` API：官方接口页对额外用户态签名的要求仍存在表述冲突，尚无账号实测证据。后台账单自动对账也未实现；真实通知、退款结果与账单一致性是后续发布验收项。

## 完成判断与推翻条件

本轮代码与隔离测试交付已具备证据，整体真实支付上线验收仍有明确未完成项。代码层置信度高；平台资格、真实凭据、iOS/IAP、真实通知与账单尚无通过证据。

开通后如实际身份、商品/金额、环境、平台单号或签名格式与冻结模型不同，必须保持支付关闭，保存原始回执并修正对应适配后重验。网络错误、客户端取消、没有通知或后台已受理都不能当成未付款、已退款或已结算。发布开关关闭不撤销已保存的付款和退款事实。

本次根因是支付与权益原本由本地模拟状态决定；修复将权威状态移到服务端已认证事实，并让前端仅读取。可复用经验已随接口边界和验收证据写入本项目文档；不新增 Memory、Skill、Hook 或全局规则。
